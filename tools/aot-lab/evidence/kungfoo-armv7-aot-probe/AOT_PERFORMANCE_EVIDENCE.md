## Claims and measurement rules

**PROVEN within this loader-stage trace — execution accounting and fallback classification.** Raw sources: each run's `interpreter-trace.txt`, `translation-manifest.json`, `aot-stage-result.json`, seven `performance-*-stage-result.json`, and `aot-checkpoints.txt`. `tools/aot-lab/kungfoo_stage_differential.py` replays the 29,578 interpreter trace rows against generated fast-block lengths. It independently derives 27,999 AOT instructions in 7,244 dynamic fast-block dispatches, 294 unsupported-encoding lookup misses at 16 unique PC/modes, 629 IT-state interpreter instructions, and 656 SVC interpreter instructions. There are zero missing-translation misses. `27,999 + 294 + 629 + 656 = 29,578`; all seven performance runs in each CI job report the same counts, no guard miss, and no step-limit miss. Thus AOT executed 94.66% of this trace, interpreter fallback excluding SVC executed 923 instructions (3.12%), and SVC executed 656 (2.22%). `tools/aot-lab/audit_fallback_encodings.py` replays the same path and uses Capstone to classify the 294 encodings; the final run's `fallback-encoding-audit.json` records 147 `LDREX` and 147 `STREX` dynamic instructions. This is an ARM exclusive-access coverage gap in the current translator, not a game-identity branch. These counts describe this trace only.

**PROVEN within checked observables — semantic agreement.** Raw sources: each run's `interpreter-trace.txt`, `aot-checkpoints.txt`, `baseline-hosts.txt`, `aot-hosts.txt`, all fourteen paired performance host logs and stage JSON files, and `differential.json`. The separately instrumented diagnostic AOT pass matches 27,999 pre-instruction PC/CPSR/r0-r14 checkpoints against forward interpreter trace rows. The 603 ordered host-call records match byte-for-byte. `passed`, mount, ELF registration, DEX load, JNI OnLoad status/version, native SO byte count, and error fields match. Seven uninstrumented fast AOT samples per run preserve these host records and observables. This does not prove all ARM states or all instructions in all programs; in particular, the fast performance pass does not emit per-instruction checkpoints. Existing ARM-exclusive behavior between AOT memory writes and interpreter fallback outside this trace remains unproven.

**PROVEN for the measured execution intervals — route timing and cold penalty.** Raw sources: the seven `baseline-performance-*-stage-result.json` and seven `performance-*-stage-result.json` files in each run; calculation in `tools/aot-lab/kungfoo_stage_differential.py`. `CLOCK_MONOTONIC` directly encloses `arm_interp_run` for baseline and `agr_aot_drive` for AOT. AOT route time is `aot_drive_seconds + fallback_interpreter_seconds + svc_interpreter_seconds`; both sides include all 29,578 guest instructions. Loader/linker and Runtime boundary dispatch are excluded from this route comparison. The seven samples are paired by sample number within one CI job. Units below are microseconds; `speedup` is the ratio of route medians, not the median of ratios.

It cannot refute the AOT route.

Component medians need not sum to the route median because each is computed independently. The 7,244 block lookups/function dispatches are included in the drive interval, not timed separately from generated ARM semantics. Their time is bounded above by the measured drive interval, but the evidence cannot assign a precise percentage to lookup versus generated operations. Runtime boundary time is reported separately and is excluded from both engine intervals; it is not an AOT-only cost. The 923 fallback instructions consume a measured 56–67 microsecond median and are not hidden in the drive figure. No performance conclusion is based on a stage-wall residual. The current trace shows a warm guest-engine advantage despite remaining lookup and fallback work; this does not identify one unique bottleneck for a full game.

**PROVEN preparation and code-size cost for this trace.** Raw sources: each `translation-manifest.json`, `aot-compile-time.txt`, generated `aot_blocks.c`, and the final run's `aot_blocks.o` / `aot-object-sections.txt`. Offline translation wall time was 1.630, 1.321, and 1.829 seconds respectively. Generated C is 1,838,285 bytes in every run; generation records 4,119 diagnostic blocks and 650 fast blocks. AOT C compilation wall time was 3.72, 4.09, and 4.77 seconds respectively. The final ARM64 object is 1,134,424 bytes on disk; `xcrun size -m` reports 551,240 bytes of `__TEXT,__text` and 867,672 total segment bytes. These are one-trace preparation and code-size measurements; whole-library storage and amortization remain **UNPROVEN**.

**SUPPORTED — common ARM capability, not a game patch.** The translation manifest records decoded operation kinds and emitted fast blocks. `tools/aot-lab/translate.py` selects by ARM/Thumb instruction encoding and CPU mode; `Runtime/AotLab/agr_aot.c` dispatches by guest PC only as a generated block lookup key. No package name, game identity, or selected guest-PC conditional was added to the backend. The code delta from the earlier Gloomy AOT proof is a set of ARM operation implementations and generic dispatch changes; the KungFoo path supplies trace data only. This supports cross-workload reuse of one backend, but two workloads do not prove library-wide coverage. The current exclusive-access and IT-state fallback counts identify remaining generic ARM capability work.

## Route implication

The diagnostic per-instruction scaffold has been removed from the measured fast path: it executes 650 compiled fast blocks with 7,244 dynamic dispatches for 27,999 instructions, with no checkpoint or trace writes in performance mode. Correctness still passes in its separate diagnostic pass; the uninstrumented pass preserves observable and host-call equality. Three independent ARM64 CI jobs show a repeated warm guest-engine speed advantage with explicit fallback and preparation costs. These facts satisfy this phase's evidence threshold to **continue AOT as a primary-route candidate**. They do not authorize naming it the primary route or changing D011. Actual full-game playable performance, physical-device behavior, whole-library code size, and exact lookup-versus-generated-time attribution remain **UNPROVEN**. No evidence here proves a structural AOT performance blocker and no architecture/ownership/scope change is required, so `DECISION_REQUIRED` is not triggered.
