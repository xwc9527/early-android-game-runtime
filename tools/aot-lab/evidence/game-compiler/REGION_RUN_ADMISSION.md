# Region compiler run admission

Question: does a register-resident, directly chained offline region compiler preserve AGR architectural state and fallback handoff on the two fixed ARMv7 workloads, and does changing block execution structure reduce dynamic dispatch, code size or guest-engine time relative to the archived per-block generated-C and direct-assembly runs?

Current uncertainty: local static generation establishes region counts, direct-edge candidates and guard placement, but cannot compile and execute `arm64-apple-ios-simulator` output or observe actual dynamic chaining, host calls, guest state and performance. The previous direct-assembly run retained the original per-block execution model and cannot answer this question.

Outcome A: matching interpreter differential and measured structural advantage supports the region architecture for further compiler work. Outcome B: a differential mismatch isolates a compiler correctness defect; matching differential without structural advantage rejects this implementation, without rejecting every specialized compiler design. The fixed Gloomy and KungFoo inputs are sufficient for this comparison; no new workload or Android laboratory work is needed.

The first KungFoo/Gloomy run reused the direct emitter's 16 operation classes and passed, but KungFoo compiled only 11,498/29,703 instructions. Its 0.171× interpreter ratio therefore cannot isolate region execution architecture from avoidable frontend misses. The next run reuses all operation kinds already implemented by the generated-C baseline, splits blocks after guest writes, and records actual chained-block count. It changes no Android or guest semantics. This full-capability A/B is needed before judging the region execution structure.

The full-capability run passed both fixed workloads and measured 6,633 chained KungFoo blocks, but emitted 10,082,896 ARM64 text bytes and ran at 0.392× the interpreter on the measured path, compared with 5,404,896 bytes and 0.490× for generated-C. The object also includes 1,950,394 bytes of text constants, largely per-block expected instruction byte arrays. The next single structural change references a validated, immutable snapshot of the already-owned original ARMv7 ELF for every block guard. It preserves the guard comparison at each block entry and the guest-write split rule. A/B outcomes: if text/object size and timing improve while differential passes, duplicate code-byte materialization is a confirmed avoidable cost; if not, this architecture still lacks a production advantage. A native macOS/iOS run is required to measure optimizer output and executed semantics.

The guard-snapshot KungFoo run passed interpreter differential and reduced ARM64 text to 7,479,436 bytes, but guest-engine speed remained 0.369× interpreter against 0.490× for the generated-C baseline. Inspection of the emitted Mach-O region function shows a sparse PC comparison tree at entry. The next focused change passes the already resolved block's ordinal through compiler-private metadata so each region selects a dense entry label. Question: does removing this repeated sparse entry search improve the same fixed execution path while preserving state, fallback, and byte guards? Outcome A is matching differential with smaller or faster code, isolating the entry cost. Outcome B is matching differential without advantage, narrowing the residual cost to local state, guards, or block semantics. A mismatch is a compiler defect. Local generation cannot measure the optimized AArch64 branch structure or guest execution time, so one macOS Gloomy/KungFoo pair is admitted.

The generated C keeps guest registers in a region-local array. The compiler may allocate some values to host registers, but complete host register residency has not been established; the next manifest reports this limit explicitly.
