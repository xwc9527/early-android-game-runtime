# AOT performance attribution run admission

Question: can the exact entry register/CPSR state and sparse guest memory pages for the two trace-selected real compiled segments be captured during the existing iOS Simulator executions, so interpreter and translated payload can be replayed from identical inputs before any timing judgment?

Current uncertainty: the archived instruction traces contain pre-instruction registers and CPSR but omit the contents of pages read and written by the selected segments. The interpreter, generated-C, and region compiler cannot be compared on the same initial guest memory state from source inspection or those traces alone. The capture writes the selected entry state, the guest pages actually touched according to the archived path, and the exact original ELF bytes. It is test-only, runs once before the selected compiled entry, and does not change the game result.

Outcome A: both fixtures are captured, their PC/register/CPSR identities match the archived trace, and interpreter replay reaches the archived post-state. This admits repeated layered timing on the same real guest region. Outcome B: capture or replay differs. Then the fixture is invalid and the first mismatch must be isolated before timing. No compiler or Runtime optimization is authorized by either outcome.

Why macOS/Simulator: only the existing real Gloomy and KungFoo execution paths can provide the original guest memory at the selected entry. This run records fixtures; it is not a performance result. Both selections are reproducible from the committed trace selector and `selected_regions.json`; the translator still consumes ELF only.

The captured Gloomy fixture passed PC, register, CPSR, page-list and ELF identity checks in run `36462537640`. The next admitted run uses that exact fixture (and the corresponding KungFoo fixture once available) to execute the selected segment with the interpreter, generated-C and indexed-region backends inside one simulator job. Its first purpose is to verify equal final registers, CPSR, control-flow PC, guest page hash and instruction count. Its second purpose is to obtain five raw paired timing samples on identical input. If any equality check fails, timing is invalid and no route claim follows. A local Windows run cannot execute the iOS Simulator ARM64 objects or the existing aarch64-apple-ios-sim interpreter archive.

KungFoo capture run `36462540748` also passed the same identity checks. The replay now includes a fourth guardless direct-entry region built from the same ELF decoder for the selected real segment. It removes code guards, region lookup, dispatcher entry, and block bookkeeping, while retaining the current local `regs[16]`/CPSR representation and actual guest memory operations. It is therefore a useful isolation of integration overhead, **not** a claim that the pure semantic L1 or host register residency has already been measured. The interpreter and all three compiled variants must first pass identical post-state and guest-page checks. The Mach-O analyzer records final machine instructions for the selected compiled symbols; source-level counts are not used as machine-code proof.

Scalar comparison admission (runs `36465706509`, `36465711305`): the initial paired replay passed on both games, but the local guest register array was visibly stack-backed in optimized ARM64. Question: does ELF-derived scalar lowering of the same operations, without global dispatch or guard, preserve the exact result and make host register residency effective? A pass excludes ARM semantics as the reason the current C representation spills; a mismatch rejects the scalar prototype. macOS ARM64 machine code and Simulator execution are required. Both runs passed state, memory and instruction equality.

Guard/accounting admission (runs `36466838211`, `36466841533`): the guardless KungFoo segment was much faster than the indexed region, but that pair removed both per-block byte guards and accounting. Question: which component adds host instructions and measurable runtime cost on exactly the same decoded CFG? The guarded-only, accounted-only and combined variants change one switch at a time, retain the same architectural output, and run interleaved with the same snapshot. A differential mismatch rejects the affected variant; indistinguishable noisy timings cannot establish a precise nanosecond split. Both runs passed correctness; machine-code counts show the guard adds more static host instructions on KungFoo.

Guard-once admission (runs dispatched from `3b10dbc`): KungFoo executes 62 dynamic block entries but only eight distinct blocks in the selected 237-instruction segment. The test-only change retains code-byte validation, caches each block's successful validation within one region entry, and invalidates the cache after every guest store. Question: does that single evidence-directed guard-placement change preserve full interpreter equality and reduce measured cost relative to per-entry guards? Outcome A is equality plus stable paired benefit; outcome B is any mismatch or no stable benefit, which rejects this correction. Source inspection alone cannot establish the optimized ARM64 cost or verify execution across the guest store and repeated loop. The existing two real-segment Simulator jobs are the narrowest executable comparison on the same iOS toolchain.
