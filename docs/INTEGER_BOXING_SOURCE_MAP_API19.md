# API19 libcore integer boxing cluster

The validated Migration Books for Frozen Bubble, Gloomy Dungeons 2, and Vector Pinball contain five observed entries in this semantic owner: `valueOf(int)`, `intValue()`, `longValue()`, `floatValue()`, and `equals(Object)`. The reproducible cross-game cluster seed is in `tools/reference-lab/evidence/integer-boxing-source-seed.json`: eight game-entry observations totaling 41,776 calls. `intValue()` alone accounts for 29,815. These counts prioritize source review; they do not limit the cluster to the values or methods those games used.

The semantic owner is `platform/libcore@9b24ebf95f897a75c60c9c68d00694406afa6fbc`, `luni/src/main/java/java/lang/Integer.java` (SHA-256 `5aae098f5c2fd832bd739fead6f04586ccbb98e6606c22ede64001ae573420a3`). `Integer.valueOf(int)` at line 705 returns the shared `SMALL_VALUES[i + 128]` for `-128 <= i < 128` and constructs a new `Integer` outside that interval. The static initializer at lines 712-718 constructs the 256 cached objects. The `Integer(int)` constructor at line 88 stores `value`; `intValue()` at line 311 returns it. `Number.Number()` is the superclass constructor in `Number.java` (SHA-256 `ccbc3f77f43e7089cf715c2a40d99d6eecba675071e8b987865619f5f4c0c0b6`). The cluster is boxing, cached identity, initialization, and lifetime together, not a single `valueOf` replacement.

The class-verification branch is mode-dependent. Pinned `dalvik/vm/Init.cpp` defaults to `VERIFY_MODE_ALL` and `OPTIMIZE_MODE_VERIFIED`, accepts command-line overrides, and `analysis/DexPrepare.cpp` changes boot-class verification expectations by mode. All four paired references record an empty `dalvik.vm.dexopt-flags` property. Pinned `AndroidRuntime.cpp` adds verify/dexopt overrides only when that property is nonempty; `app_main.cpp` forwards the VM arguments from the built TRACE ramdisk's `init.rc`, whose Zygote command contains `-Xzygote` but no verify/dexopt override. This closes the effective-mode evidence edge for this reference configuration, not the verification and optimization owner.
`dvmVerifyClass` iterates both direct and virtual methods; `DexVerify.cpp:verifyMethod` builds instruction metadata and calls `CodeVerify.cpp:dvmCreateUninitInstanceMap` and `dvmVerifyCodeFlow`. These files are pinned as part of `Dalvik.ClassVerification`; the owner remains `SOURCE_LOCATED` while the verifier's complete control-flow, failure, and AGR contracts are reviewed.

This is source-derived expansion from an observed libcore entry. It is not a claim that the games dynamically observed every Dalvik internal call. The supporting records remain `SOURCE_LOCATED`; they cannot be promoted by changing edge status strings. The closure gate now checks each edge against a separate, reviewed source-owner record and verifies its pinned files in the local AOSP checkout.
External owner reviews must account for their own dependency edges and declared platform boundary contracts; nested cross-owner edges are checked recursively. A `SOURCE_CLOSED_EXTERNAL` review must reference the matching closed owner record by its canonical digest. This prevents a string-level assertion from authorizing the Integer port.
The generated Source Manifest now materializes nine reachable source-derived owners with their parent observed `Integer.valueOf(int)` dependency ID and full edge paths. Six remain `SOURCE_LOCATED`; the narrowly scoped static-field array-root, Zygote VM-options, and init.rc launch-argument owners are `SOURCE_CLOSED`. The allocation and OOME paths were combined into one owner after their reciprocal source calls exposed an artificial cross-owner cycle. None carries migration authority or claims direct game observation.

The four-game TRACE run manifest lists only `APP_DEX_TO_BOOT_METHOD_INVOKE` in `observer_coverage`. It does not supply a class-initialization event for `Integer`, so that edge's provenance is the pinned `Integer.valueOf` source path, Dalvik source, and Framework preload source, not a newly claimed app-triggered runtime observation. All four qualified paired TRACE records report `PRELOADED_IN_ZYGOTE` with the same configured-list SHA-256 as the pinned `preloaded-classes` file, which contains `java.lang.Integer`; each lists only `java.lang.UnsafeByteSequence` as a failed class. Frozen Bubble's record reports 2778 configured and 2777 completed. Thus Integer is `PRELOADED/INHERITED` in these API19 references. This does not justify removing any unobserved VM path.

All five direct cross-cluster source edges and their nested paths are pinned in the libcore index and verified against the local Dalvik, Framework, and system/core checkouts by `verify_source_index.py`. The static-field array-root edge is `SOURCE_CLOSED` for the narrow path above; the preload, initialization, allocation, and constructor invocation edges remain `SOURCE_LOCATED`.

`Tests/DexLoom/lifetime-host.c` now covers a static field holding an object array whose element must survive minor, major, and incremental GC; after clearing the static field, major GC must reclaim both. The WSL host contract passed all of these checks. It proves AGR's existing root traversal for this pattern, not that Integer cache construction or the complete allocation/OOME path has been migrated.

The allocation-failure gap is concrete: API19 `throwOOME()` sets a pending Java exception, using the VM-rooted stock object when a thread is not yet rooted or exception allocation recurses. AGR `dx_vm_alloc_object_locked()` currently returns `NULL` with `error_msg` at a full heap and does not set `pending_exception`; its `dx_malloc` failure path does the same. The stock OOME startup, root, and propagation chain remains `SOURCE_LOCATED`, so this finding is a closure task rather than authority to add an isolated error patch.

The current AGR counterpart in `Runtime/DexLoom/AndroidMini/dx_android_framework.c` allocates a fresh boxed object on every `Integer.valueOf` call and registers a second `Integer` class with `Object` as superclass. `Runtime/DexLoom/VM/dx_vm.c` first registered an `Integer extends Number`; its class hash replaces that descriptor's boot-loader entry when the second class is registered. Both classes remain in `vm->classes`, while the hash lookup selects the second. The second class has no `SMALL_VALUES` static field, is marked initialized without `<clinit>`, and has an `equals` handler that always returns false. AGR's major, minor, and incremental GC paths scan class static fields and object-array elements, but that mechanism is not yet connected to an Integer cache. These are source-backed implementation differences, not yet a measured API19-to-AGR differential. No production change is authorized while class initialization, static-field identity, and GC integration remain unclosed.

The `intValue`, `longValue`, `floatValue`, and `equals` entry source sets are now `SOURCE_CLOSED`: their pinned method bodies have no internal source callee, JNI, resource, or service edge beyond their stored value and `Number` type contract. This does not authorize moving them one by one. `valueOf(int)` and the whole `libcore.IntegerBoxing` cluster remain `SOURCE_LOCATED`; `MIGRATION_AUTHORIZED` is false. The remaining chain is preload inheritance, Dalvik class initialization/allocation, and AGR boot-class ownership. Only a reviewed cluster Source Manifest can authorize replacing the synthetic boxing path and entering a focused CLEAN differential.
